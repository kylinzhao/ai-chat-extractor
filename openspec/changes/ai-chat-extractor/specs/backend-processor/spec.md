# Backend Processor Spec

## 新增需求

### 需求:后端必须提供接收插件数据的 API 端点
系统必须提供一个 HTTP POST 端点，用于接收浏览器插件发送的对话数据。该端点必须验证数据格式，并返回适当的响应。

#### 场景:成功接收对话数据
- **当** 插件发送符合格式要求的对话数据到 `/api/conversations` 端点
- **那么** 系统必须返回 HTTP 201 状态码
- **并且** 必须在响应中包含新创建的对话记录 ID
- **并且** 必须触发异步处理流程（AI 生成总结）

#### 场景:数据格式验证失败
- **当** 插件发送的数据缺少必需字段（platform、messages、captured_at）
- **那么** 系统必须返回 HTTP 400 状态码
- **并且** 必须在响应中包含具体的验证错误信息
- **并且** 不得创建任何数据库记录

#### 场景:处理服务器内部错误
- **当** 处理请求时发生未预期的服务器错误
- **那么** 系统必须返回 HTTP 500 状态码
- **并且** 必须记录错误日志
- **并且** 不得暴露敏感的系统信息

### 需求:后端必须持久化存储对话数据
系统必须将接收到的对话数据（包括元数据、消息、图片 URL）持久化存储到数据库。每个对话记录必须对应一个唯一的 Summary_Group。

#### 场景:创建新对话记录
- **当** 后端成功接收并验证对话数据
- **那么** 系统必须在数据库中创建新的对话记录
- **并且** 必须生成唯一的记录 ID
- **并且** 必须保存所有字段：平台、模型版本、抓取时间、消息、图片 URL
- **并且** 必须设置初始状态为"processing"（正在处理）

#### 场景:关联总结记录
- **当** 对话记录创建成功
- **那么** 系统必须创建对应的 Summary_Group 记录
- **并且** Summary_Group 必须关联到对话记录 ID
- **并且** Summary_Group 的初始状态必须为"pending"（等待生成）

#### 场景:数据库连接失败
- **当** 数据库连接失败或写入错误
- **那么** 系统必须返回 HTTP 500 状态码
- **并且** 必须记录详细的错误日志
- **并且** 必须通知用户（如果可能）存储失败

### 需求:后端必须调用 DeepSeek API 生成详细汇总
系统必须在接收对话数据后，调用 DeepSeek API（V3 或 R1 模型）生成详细的对话汇总。汇总应当提炼逻辑、要点、知识点，适用于笔记管理软件。

#### 场景:成功生成详细汇总
- **当** 对话记录创建成功且状态为"processing"
- **那么** 系统必须调用 DeepSeek API
- **并且** 必须使用预配置的"详细汇总"提示词模板
- **并且** 必须将对话历史作为上下文传递
- **并且** API 响应成功后，必须将汇总内容保存到 Summary_Group
- **并且** 必须更新记录状态为"completed"

#### 场景:DeepSeek API 调用失败
- **当** DeepSeek API 返回错误（超时、限流、服务不可用）
- **那么** 系统必须记录错误日志
- **并且** 必须将记录状态更新为"failed"
- **并且** 必须在 Summary_Group 中保存错误信息
- **并且** 必须提供重试机制（最多 3 次）

#### 场景:API 配额不足
- **当** DeepSeek API 返回配额不足错误
- **那么** 系统必须标记记录为"quota_exceeded"状态
- **并且** 必须通知管理员检查 API 配额
- **并且** 不得自动重试（避免浪费请求）

### 需求:后端必须调用 DeepSeek API 生成社媒摘要
系统必须使用"去 AI 化"的提示词策略，生成适合社交媒体分享的短小精悍文案。社媒摘要必须独立于详细汇总，单独存储。

#### 场景:生成社交媒体摘要
- **当** 对话记录创建成功
- **那么** 系统必须并行调用 DeepSeek API 生成社媒摘要
- **并且** 必须使用专门的"社媒摘要"提示词模板
- **并且** 提示词必须包含"去 AI 化"指令（避免"总之"、"综上所述"等词汇）
- **并且** 生成的摘要必须限制在 280 字以内（适合微博、即刻等平台）
- **并且** 必须将社媒摘要保存到 Summary_Group 的独立字段

#### 场景:社媒摘要风格控制
- **当** 调用 DeepSeek API 生成社媒摘要
- **那么** 提示词必须设定角色为"资深博主或技术专家"
- **并且** 必须要求模拟朋友圈、即刻等平台的日常分享风格
- **并且** 必须突出金句和核心结论
- **并且** 必须避免列表式总结，优先段落式表达

#### 场景:摘要生成失败
- **当** 社媒摘要生成失败
- **那么** 系统必须记录错误
- **并且** 不得影响详细汇总的存储
- **并且** 可以使用详细汇总的截断版本作为备用摘要

### 需求:后端必须管理对话与总结的关联关系
系统必须确保一个原始对话对应一个 Summary_Group。Summary_Group 必须包含原始对话、详细汇总、社媒摘要、生成时间戳、状态等字段。

#### 场景:创建 Summary_Group
- **当** 接收到新的对话数据
- **那么** 系统必须创建新的 Summary_Group 记录
- **并且** 必须包含以下字段：
  - `conversation_id`: 关联的对话记录 ID
  - `detailed_summary`: 详细汇总内容（AI 生成）
  - `social_summary`: 社媒摘要内容（AI 生成）
  - `original_conversation`: 原始对话 JSON
  - `status`: 处理状态（pending/processing/completed/failed）
  - `created_at`: 创建时间
  - `updated_at`: 更新时间
- **并且** 关系必须是一对一（一个对话对应一个 Summary_Group）

#### 场景:查询对话及其总结
- **当** 通过 Web 平台查询对话记录
- **那么** 系统必须返回完整的 Summary_Group 数据
- **并且** 必须包含原始对话和所有 AI 生成的内容
- **并且** 必须按创建时间倒序排列

#### 场景:删除对话记录
- **当** 管理员删除对话记录
- **那么** 系统必须物理删除对应的 Summary_Group
- **并且** 必须删除关联的渲染图片（如果有）
- **并且** 操作必须是原子性的（全部成功或全部失败）

### 需求:后端必须支持 CORS 和安全验证
系统必须正确处理跨域请求，并实现基本的安全验证机制，防止未授权访问和数据注入。

#### 场景:处理预检请求
- **当** 浏览器发送 OPTIONS 预检请求
- **那么** 系统必须返回正确的 CORS 头
- **并且** 必须允许插件来源的请求
- **并且** 必须返回 HTTP 204 状态码

#### 场景:验证请求来源
- **当** 接收到插件发送的数据
- **那么** 系统必须验证请求的 Origin 头
- **并且** 必须拒绝来自未授权域名的请求
- **并且** 必须返回 HTTP 403 状态码

#### 场景:输入数据清理
- **当** 接收对话数据
- **那么** 系统必须清理和验证所有输入字段
- **并且** 必须防止 SQL 注入、XSS 攻击
- **并且** 必须限制消息内容的最大长度（如 100,000 字符）

### 需求:后端必须提供查询和管理 API
系统必须提供 RESTful API 端点，用于 Web 平台查询、更新、删除对话记录。这些端点必须支持分页、筛选、排序。

#### 场景:查询所有对话记录
- **当** Web 平台请求 GET `/api/conversations`
- **那么** 系统必须返回所有对话记录的列表
- **并且** 必须支持分页参数（page、per_page）
- **并且** 必须支持筛选参数（status、platform）
- **并且** 必须按创建时间倒序排列

#### 场景:查询单个对话记录
- **当** Web 平台请求 GET `/api/conversations/:id`
- **那么** 系统必须返回指定 ID 的完整记录
- **并且** 必须包含 Summary_Group 的所有数据
- **并且** 如果记录不存在，必须返回 HTTP 404

#### 场景:更新对话记录
- **当** Web 平台请求 PATCH `/api/conversations/:id`
- **那么** 系统必须允许更新以下字段：
  - `social_summary`: 手动修改的社媒摘要
  - `detailed_summary`: 手动修改的详细汇总
  - `visibility`: 公开/隐藏状态
- **并且** 必须更新 `updated_at` 时间戳
- **并且** 必须返回更新后的记录

#### 场景:删除对话记录
- **当** Web 平台请求 DELETE `/api/conversations/:id`
- **那么** 系统必须物理删除该记录
- **并且** 必须级联删除关联的 Summary_Group 和渲染图片
- **并且** 必须返回 HTTP 204 状态码

### 需求:后端必须支持批量操作
系统必须支持批量更新可见性状态、批量删除记录等操作，以提高管理效率。

#### 场景:批量更新可见性
- **当** Web 平台请求 POST `/api/conversations/batch-update-visibility`
- **那么** 系统必须接受记录 ID 数组和目标状态
- **并且** 必须批量更新所有指定记录的 visibility 字段
- **并且** 必须返回成功更新的记录数量
- **并且** 如果部分记录不存在，必须跳过并继续处理其他记录

#### 场景:批量删除记录
- **当** Web 平台请求 POST `/api/conversations/batch-delete`
- **那么** 系统必须接受记录 ID 数组
- **并且** 必须批量删除所有指定记录
- **并且** 必须级联删除关联数据
- **并且** 必须返回成功删除的记录数量

### 需求:后端必须记录操作日志
系统必须记录所有关键操作的日志，包括数据接收、API 调用、错误信息，便于问题追踪和系统监控。

#### 场景:记录数据接收日志
- **当** 接收到新的对话数据
- **那么** 系统必须记录以下信息：
  - 接收时间
  - 来源平台
  - 消息数量
  - 处理状态
- **并且** 日志级别必须是 INFO

#### 场景:记录 API 调用日志
- **当** 调用 DeepSeek API
- **那么** 系统必须记录以下信息：
  - API 调用时间
  - 请求类型（详细汇总/社媒摘要）
  - 响应时间（latency）
  - 成功或失败状态
- **并且** 如果失败，必须记录错误详情

#### 场景:记录错误日志
- **当** 系统发生任何错误
- **那么** 系统必须记录详细的错误堆栈
- **并且** 必须包含错误发生的上下文信息
- **并且** 日志级别必须是 ERROR
- **并且** 不得在日志中暴露敏感数据（API 密钥、用户隐私内容）

## 修改需求

无（这是新增功能）
