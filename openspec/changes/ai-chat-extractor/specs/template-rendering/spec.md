# Template Rendering Spec

## 新增需求

### 需求:系统必须提供 HTML 模板用于渲染社媒摘要
系统必须提供至少三种内置的 HTML 模板（Bento UI、Newsletter、复古信纸），用于将社媒摘要渲染为可分享的图片。模板必须支持变量替换，以填充动态内容。

#### 场景:Bento UI 模板可用
- **当** 用户选择 Bento UI 模板渲染分享图
- **那么** 系统必须使用 Bento UI HTML 模板
- **并且** 模板必须呈现现代化卡片布局
- **并且** 必须支持以下变量：
  - `{{title}}`: 对话标题或主题
  - `{{content}}`: 社媒摘要内容
  - `{{platform}}`: 来源平台图标和名称
  - `{{date}}`: 生成日期
  - `{{footer}}`: 底部标识或品牌信息
- **并且** 样式必须体现专业科技感

#### 场景:Newsletter 模板可用
- **当** 用户选择 Newsletter 模板渲染分享图
- **那么** 系统必须使用 Newsletter HTML 模板
- **并且** 模板必须模拟专业订阅邮件的排版
- **并且** 必须支持 Bento UI 模板的所有变量
- **并且** 样式必须克制、简洁，类似优质 Newsletter

#### 场景:复古信纸模板可用
- **当** 用户选择复古信纸模板渲染分享图
- **那么** 系统必须使用复古信纸 HTML 模板
- **并且** 模板必须模拟物理信纸或笔记本的质感
- **并且** 必须支持 Bento UI 模板的所有变量
- **并且** 样式必须适合感性思考分享

#### 场景:模板变量替换
- **当** 系统使用模板渲染内容
- **那么** 必须将所有模板变量替换为实际值
- **并且** 如果某个变量无值，必须使用默认值或空字符串
- **并且** 不得在最终输出中包含未替换的变量标记（如 `{{title}}`）

### 需求:系统必须使用 Puppeteer 进行 HTML 渲染
系统必须使用 Puppeteer 启动 Headless Chrome 浏览器，将填充后的 HTML 模板渲染为图片。渲染过程必须在后端完成，不得依赖前端浏览器。

#### 场景:启动 Headless Chrome
- **当** 系统接收到渲染请求
- **那么** 必须启动 Puppeteer 实例
- **并且** 必须配置为 headless 模式（无图形界面）
- **并且** 必须设置适当的视口大小（如 1200x1600 像素）
- **并且** 必须禁用不必要的功能以提高性能

#### 场景:加载 HTML 内容
- **当** Puppeteer 页面启动完成
- **那么** 系统必须加载填充后的 HTML 内容
- **并且** 必须等待所有资源（字体、图片）加载完成
- **并且** 必须设置合理的超时时间（如 30 秒）
- **并且** 如果超时，必须记录错误并返回失败

#### 场景:生成 @2x 高清截图
- **当** HTML 内容加载完成
- **那么** 系统必须使用 Puppeteer 的 screenshot 功能
- **并且** 必须设置设备像素比为 2（@2x）
- **并且** 必须输出为 PNG 格式
- **并且** 必须确保文字和图形清晰可读

#### 场景:保存渲染结果
- **当** 截图生成成功
- **那么** 系统必须将图片保存到文件系统或对象存储
- **并且** 必须生成唯一的文件名（如 UUID）
- **并且** 必须将图片 URL 保存到数据库的 Summary_Group 记录中
- **并且** 必须更新记录状态为"rendered"

### 需求:系统必须支持模板选择和自定义
系统必须允许用户在 Web 管理后台选择渲染模板，并支持预览效果。高级用户必须能够上传自定义模板。

#### 场景:选择渲染模板
- **当** 用户在管理后台查看对话记录
- **那么** 系统必须显示模板选择器（下拉菜单或卡片选择）
- **并且** 必须列出所有可用模板（Bento UI、Newsletter、复古信纸）
- **并且** 必须显示每个模板的缩略图预览
- **并且** 选择模板后必须触发重新渲染

#### 场景:预览渲染效果
- **当** 用户点击"预览"按钮
- **那么** 系统必须生成当前选择的模板预览
- **并且** 必须在模态框或新标签页中显示预览图
- **并且** 预览必须是实时渲染的（非缓存图片）
- **并且** 预览生成时间不得超过 10 秒

#### 场景:上传自定义模板
- **当** 高级用户上传自定义 HTML 模板
- **那么** 系统必须验证 HTML 格式的合法性
- **并且** 必须确保模板包含必需的变量标记
- **并且** 必须将模板保存到用户的模板库
- **并且** 必须在模板列表中标记为"自定义模板"

#### 场景:自定义模板变量验证
- **当** 用户上传自定义模板
- **那么** 系统必须检查模板是否包含所有必需变量
- **并且** 如果缺少必需变量，必须拒绝上传并说明原因
- **并且** 必须支持额外变量（使用默认值填充）

### 需求:系统必须处理渲染失败和重试
系统必须捕获渲染过程中的各种错误（Puppeteer 启动失败、HTML 加载超时、截图失败），并提供重试机制。

#### 场景:Puppeteer 启动失败
- **当** Puppeteer 无法启动 Headless Chrome
- **那么** 系统必须记录错误日志
- **并且** 必须将记录状态更新为"render_failed"
- **并且** 必须在 Summary_Group 中保存错误信息
- **并且** 必须提供"重试渲染"按钮

#### 场景:HTML 加载超时
- **当** HTML 内容在 30 秒内未能完成加载
- **那么** 系统必须中断渲染过程
- **并且** 必须记录超时错误
- **并且** 必须标记记录为"render_timeout"状态
- **并且** 不得占用 Puppeteer 实例资源

#### 场景:截图生成失败
- **当** Puppeteer 截图功能抛出错误
- **那么** 系统必须记录错误详情
- **并且** 必须释放 Puppeteer 实例
- **并且** 必须提供重试机制（最多 3 次）
- **并且** 如果 3 次均失败，必须标记为"permanent_failure"

#### 场景:重试渲染
- **当** 用户点击"重试渲染"按钮
- **或者** 系统自动重试
- **那么** 系统必须重新启动 Puppeteer 实例
- **并且** 必须使用相同的模板和内容
- **并且** 必须在数据库中记录重试次数
- **并且** 最多重试 3 次

### 需求:系统必须优化渲染性能
系统必须实现渲染性能优化，包括 Puppeteer 实例池、资源缓存、并行处理等，确保在高并发情况下的稳定性。

#### 场景:使用 Puppeteer 实例池
- **当** 系统启动时
- **那么** 必须预启动一定数量的 Puppeteer 实例（如 3-5 个）
- **并且** 必须将实例保存在池中，避免频繁启动
- **并且** 必须实现实例的获取和释放逻辑
- **并且** 必须定期清理空闲实例

#### 场景:处理渲染请求队列
- **当** 同时收到多个渲染请求
- **那么** 系统必须将请求加入队列
- **并且** 必须按 FIFO 顺序处理
- **并且** 必须限制并发渲染数量（如最多 3 个）
- **并且** 必须向用户显示"排队中"状态

#### 场景:缓存模板资源
- **当** 渲染同一个模板多次
- **那么** 系统必须缓存模板的静态资源（CSS、字体）
- **并且** 必须避免重复加载相同资源
- **并且** 缓存必须支持失效机制（模板更新时清除）

#### 场景:监控渲染性能
- **当** 渲染操作完成
- **那么** 系统必须记录以下性能指标：
  - 渲染耗时（毫秒）
  - Puppeteer 实例获取时间
  - HTML 加载时间
  - 截图生成时间
- **并且** 必须定期分析性能瓶颈
- **并且** 如果平均渲染时间超过 15 秒，必须发出告警

### 需求:系统必须支持图片存储和访问
系统必须将生成的图片保存到持久化存储（文件系统或对象存储），并提供公开访问的 URL。

#### 场景:保存图片到文件系统
- **当** 截图生成成功
- **那么** 系统必须将图片保存到配置的存储目录
- **并且** 必须使用 UUID 作为文件名（如 `a1b2c3d4.png`）
- **并且** 可以按日期组织子目录（如 `2025/02/10/a1b2c3d4.png`）
- **并且** 必须设置适当的文件权限

#### 场景:生成公开访问 URL
- **当** 图片保存成功
- **那么** 系统必须生成公开访问的 URL
- **并且** URL 必须包含静态资源路径前缀（如 `/renders/`）
- **并且** 必须将 URL 保存到数据库
- **并且** URL 必须在 Web 平台的展示页中可访问

#### 场景:删除过期的渲染图片
- **当** 对话记录被删除
- **或者** 用户重新渲染（生成新图片）
- **那么** 系统必须物理删除旧的渲染图片
- **并且** 必须释放存储空间
- **并且** 不得留下孤立文件

### 需求:系统必须支持批量渲染
系统必须支持批量渲染多个对话记录的分享图，以便在迁移或更新模板时重新生成所有图片。

#### 场景:批量重新渲染
- **当** 管理员触发"批量重新渲染"操作
- **那么** 系统必须列出所有需要渲染的记录
- **并且** 必须按优先级排序（如按创建时间）
- **并且** 必须使用后台任务队列处理
- **并且** 必须向管理员显示进度（已完成/总数）

#### 场景:批量渲染失败处理
- **当** 批量渲染中某个记录失败
- **那么** 系统必须记录失败的记录 ID 和原因
- **并且** 必须继续处理其他记录
- **并且** 必须在完成后生成失败报告
- **并且** 不得因为单个失败而中断整个批量操作

#### 场景:批量渲染限流
- **当** 批量渲染任务数量超过阈值
- **那么** 系统必须实施限流策略
- **并且** 每秒最多处理 N 个渲染请求（如 3 个）
- **并且** 必须避免占用过多系统资源
- **并且** 必须确保 Web 平台的其他功能不受影响

### 需求:系统必须支持图片格式和尺寸配置
系统必须支持配置输出图片的格式（PNG、JPEG、WebP）、质量、尺寸等参数，以适应不同使用场景。

#### 场景:配置输出格式
- **当** 管理员配置渲染参数
- **那么** 系统必须支持选择以下格式：
  - PNG（默认，无损）
  - JPEG（较小文件）
  - WebP（现代格式，最佳压缩）
- **并且** 必须保存配置到系统设置
- **并且** 所有渲染操作必须使用配置的格式

#### 场景:配置图片质量
- **当** 管理员选择 JPEG 或 WebP 格式
- **那么** 系统必须允许配置质量参数（0-100）
- **并且** 默认质量必须是 90
- **并且** 质量必须影响文件大小和清晰度

#### 场景:配置图片尺寸
- **当** 管理员配置渲染参数
- **那么** 系统必须支持配置以下尺寸：
  - 视口宽度（默认 1200 像素）
  - 视口高度（默认 1600 像素）
  - 设备像素比（默认 2，即 @2x）
- **并且** 必须在 Puppeteer 配置中应用这些参数

## 修改需求

无（这是新增功能）

## 移除需求

无
