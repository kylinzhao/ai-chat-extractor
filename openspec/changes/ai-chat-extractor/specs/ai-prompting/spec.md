# AI Prompting Spec

## 新增需求

### 需求:系统必须提供"去 AI 化"的详细汇总提示词模板
系统必须提供专门用于生成详细汇总的提示词模板，该模板必须明确要求 AI 避免使用"总之"、"综上所述"、"首先/其次"等 AI 常用词汇，生成更像人类撰写的总结。

#### 场景:生成详细汇总提示词
- **当** 系统准备调用 DeepSeek API 生成详细汇总
- **那么** 提示词必须包含以下核心指令：
  - "你是一位经验丰富的技术博主，擅长将复杂的 AI 对话转化为结构清晰的笔记"
  - "禁止使用以下词汇：总之、综上所述、首先、其次、再者、最后、值得注意的是"
  - "使用直接陈述句，避免过度使用连接词"
  - "提炼对话的核心逻辑、关键知识点和可操作结论"
  - "使用分层结构，但避免机械的编号列表"
- **并且** 提示词必须将对话历史作为上下文附加
- **并且** 提示词必须指定输出格式（如 Markdown）

#### 场景:提示词注入对话上下文
- **当** 构造 API 请求
- **那么** 系统必须将对话历史格式化为可读的文本
- **并且** 必须保留消息的发送者标识（User/Assistant）
- **并且** 必须截断过长的对话（如超过 10,000 字符）
- **并且** 必须在提示词中说明"以下是用户与 AI 的对话内容"

#### 场景:提示词版本管理
- **当** 管理员更新提示词模板
- **那么** 系统必须保存提示词的版本历史
- **并且** 每个版本必须包含：
  - 版本号（如 v1.0、v1.1）
  - 更新时间
  - 更新说明（如"优化去 AI 化指令"）
  - 完整的提示词内容
- **并且** 系统必须支持回滚到历史版本
- **并且** 新对话必须使用最新版本的提示词

### 需求:系统必须提供社交媒体风格的摘要提示词模板
系统必须提供专门用于生成社媒摘要的提示词模板，该模板必须模拟资深博主或技术专家在朋友圈、即刻等平台的日常分享风格。

#### 场景:生成社媒摘要提示词
- **当** 系统准备调用 DeepSeek API 生成社媒摘要
- **那么** 提示词必须包含以下核心指令：
  - "你是一位在社交媒体上拥有大量关注者的技术专家，擅长用简短有力的语言分享见解"
  - "模拟朋友圈、即刻等平台的日常分享风格，轻松但不失专业"
  - "字数严格控制在 280 字以内（适合微博、即刻等平台）"
  - "必须有'金句'或核心结论，让人一眼记住"
  - "禁止使用：总之、综上所述、首先、其次、1. 2. 3. 等编号"
  - "优先使用段落式表达，避免列表堆砌"
  - "加入个人化语气词（如'这个发现太有意思了'、'强烈推荐'）"
  - "可以适当使用 emoji，但不要过度"
- **并且** 提示词必须强调"短小精悍"和"分享欲望"

#### 场景:提示词限制输出长度
- **当** 构造社媒摘要提示词
- **那么** 必须在提示词中明确字数限制："280 字以内"
- **并且** 必须提供示例："好的输出：'今天和 AI 讨论了 X，结论是 Y，这个发现改变了我的看法。'"
- **并且** 必须说明超长输出会被截断

#### 场景:提示词示例展示
- **当** 管理员查看提示词配置
- **那么** 系统必须提供"期望输出示例"
- **并且** 示例必须展示符合要求的社媒摘要：
  - 简短（150-200 字）
  - 包含金句
  - 无 AI 常用词汇
  - 有个人化语气
- **并且** 示例必须可编辑（管理员可自定义）

### 需求:系统必须支持提示词参数化和自定义
系统必须支持在提示词中使用变量，以便根据对话内容动态生成提示词。管理员必须能够自定义提示词模板。

#### 场景:提示词变量替换
- **当** 系统使用提示词模板生成 API 请求
- **那么** 必须支持以下变量：
  - `{{platform}}`: 对话来源平台（Gemini/豆包）
  - `{{model}}`: AI 模型版本
  - `{{topic}}`: 对话主题（从内容中提取）
  - `{{message_count}}`: 消息数量
- **并且** 必须在发送前替换所有变量
- **并且** 如果变量无值，必须使用默认值或移除该部分

#### 场景:自定义提示词模板
- **当** 管理员在后台编辑提示词
- **那么** 系统必须提供富文本编辑器或代码编辑器
- **并且** 必须支持变量语法高亮
- **并且** 必须提供"保存并测试"功能
- **并且** 测试时必须使用真实对话数据调用 API
- **并且** 必须显示 API 响应和成本预估

#### 场景:验证提示词合法性
- **当** 管理员保存自定义提示词
- **那么** 系统必须验证以下内容：
  - 提示词长度（100-5000 字符）
  - 是否包含必需的核心指令（如"禁止使用"）
  - 变量语法是否正确
- **并且** 如果验证失败，必须显示具体错误
- **并且** 不得保存不合法的提示词

### 需求:系统必须支持提示词 A/B 测试
系统必须支持为同一功能配置多个提示词版本，并随机分配使用，以便比较不同提示词的效果。

#### 场景:创建提示词 A/B 测试
- **当** 管理员创建 A/B 测试
- **那么** 系统必须允许添加多个提示词版本（如 A 版本、B 版本）
- **并且** 必须配置流量分配比例（如 50%:50%）
- **并且** 必须为每个版本命名和描述
- **并且** 必须设置测试开始和结束时间

#### 场景:分配提示词版本
- **当** 新对话需要生成总结
- **并且** 存在活跃的 A/B 测试
- **那么** 系统必须根据配置的比例随机选择提示词版本
- **并且** 必须在数据库中记录使用的版本 ID
- **并且** 必须确保分配均匀（如使用随机种子）

#### 场景:分析 A/B 测试结果
- **当** A/B 测试结束或管理员查看结果
- **那么** 系统必须显示每个版本的以下指标：
  - 使用次数
  - 平均生成时间
  - 平均 Token 消耗
  - 用户满意度（如果有手动评分）
- **并且** 必须提供版本对比图表
- **并且** 必须支持"优胜劣汰"（选择最佳版本并停用其他）

### 需求:系统必须监控提示词效果和成本
系统必须记录每次 AI 调用的输入 Token、输出 Token、成本，并定期分析提示词的效果。

#### 场景:记录 API 调用详情
- **当** 系统调用 DeepSeek API
- **那么** 必须在数据库中记录以下信息：
  - 调用时间
  - 使用的提示词版本 ID
  - 输入 Token 数量
  - 输出 Token 数量
  - API 响应时间（毫秒）
  - 成本（根据 Token 单价计算）
  - 成功或失败状态
- **并且** 记录必须与对话记录关联

#### 场景:计算 API 成本
- **当** API 调用完成
- **那么** 系统必须根据 DeepSeek 的定价计算成本
- **并且** 必须使用以下公式：`(input_tokens * input_price + output_tokens * output_price) / 1000000`
- **并且** 价格必须可配置（在设置中更新）
- **并且** 成本必须累计到总消耗统计

#### 场景:生成成本报告
- **当** 管理员查看成本统计
- **那么** 系统必须显示以下信息：
  - 今日/本周/本月总成本
  - 平均每条记录的成本
  - 成本趋势图表
  - 成本最高的提示词版本
- **并且** 必须支持导出 CSV 报告
- **并且** 必须设置成本告警阈值（如超过 $50 则通知）

### 需求:系统必须支持提示词热更新
系统必须支持在不停机的情况下更新提示词模板，新对话立即使用新提示词，而不影响正在处理的任务。

#### 场景:热更新提示词
- **当** 管理员保存提示词更改
- **那么** 系统必须立即将新提示词加载到内存
- **并且** 必须使旧提示词缓存失效
- **并且** 新 API 请求必须使用新提示词
- **并且** 不得重启服务或中断正在处理的请求

#### 场景:回滚提示词版本
- **当** 管理员发现新提示词有问题
- **那么** 系统必须支持一键回滚到历史版本
- **并且** 回滚必须立即生效
- **并且** 必须在操作日志中记录回滚动作
- **并且** 必须说明回滚原因（可选）

#### 场景:提示词缓存管理
- **当** 系统加载提示词
- **那么** 必须将提示词缓存到内存（避免每次读取数据库）
- **并且** 缓存必须设置合理的 TTL（如 5 分钟）
- **并且** 更新提示词时必须主动清除缓存
- **并且** 必须支持手动清除缓存（管理操作）

### 需求:系统必须提供提示词质量评估工具
系统必须提供工具帮助管理员评估提示词生成内容的质量，如手动评分、关键词检测、风格分析。

#### 场景:手动评分内容质量
- **当** 管理员查看生成的总结或摘要
- **那么** 系统必须提供评分控件（1-5 星）
- **并且** 必须允许记录评分理由（可选）
- **并且** 评分必须关联到提示词版本
- **并且** 系统必须计算每个版本的平均分

#### 场景:检测 AI 常用词汇
- **当** 系统生成内容后
- **那么** 必须自动检测是否包含禁止词汇：
  - "总之"、"综上所述"、"首先"、"其次"
- **并且** 如果检测到，必须标记为"可能不符合要求"
- **并且** 必须在管理后台高亮显示这些词汇
- **并且** 必须统计每个提示词版本的违规率

#### 场景:分析内容风格
- **当** 系统生成内容后
- **那么** 必须分析以下风格指标：
  - 平均句长
  - 词汇复杂度
  - 语气词使用频率
  - Emoji 数量
- **并且** 必须与"理想风格"对比（如人工编写的优质内容）
- **并且** 必须在管理后台显示风格评分

### 需求:系统必须支持多语言提示词
系统必须支持为不同语言配置不同的提示词模板，以适应国际化需求。

#### 场景:配置中文提示词
- **当** 对话内容主要是中文
- **那么** 系统必须使用中文提示词模板
- **并且** 提示词本身必须用中文编写
- **并且** 禁止词汇必须是中文词汇（如"总之"而非"In conclusion"）
- **并且** 风格参考必须是中文社交媒体平台（即刻、微博）

#### 场景:配置英文提示词
- **当** 对话内容主要是英文
- **那么** 系统必须使用英文提示词模板
- **并且** 提示词本身必须用英文编写
- **并且** 禁止词汇必须是英文词汇（如"In conclusion"、"Firstly"）
- **并且** 风格参考必须是英文社交媒体平台（Twitter、LinkedIn）

#### 场景:自动检测对话语言
- **当** 系统接收到对话数据
- **那么** 必须自动检测主要语言（基于前 3 条消息）
- **并且** 必须选择对应的提示词模板
- **并且** 如果检测失败，必须使用默认语言（中文）
- **并且** 管理员必须能够手动覆盖语言选择

### 需求:系统必须支持提示词模板库
系统必须提供预设的提示词模板库，管理员可以直接选择使用或作为自定义模板的基础。

#### 场景:浏览预设模板
- **当** 管理员访问提示词模板库
- **那么** 系统必须显示所有预设模板
- **并且** 每个模板必须包含：
  - 模板名称和描述
  - 适用场景（如"技术对话"、"创意讨论"）
  - 完整的提示词内容预览
  - 预期输出示例
  - 用户评价（如果有的话）
- **并且** 必须支持搜索和筛选

#### 场景:应用预设模板
- **当** 管理员选择"应用此模板"
- **那么** 系统必须将模板内容复制到当前提示词编辑器
- **并且** 必须提示"模板已应用，您可以根据需要调整"
- **并且** 必须保存模板与自定义版本的关联关系

#### 场景:贡献自定义模板
- **当** 管理员创建了高质量的提示词
- **那么** 系统必须支持"分享到模板库"
- **并且** 必须要求填写：
  - 模板名称
  - 适用场景描述
  - 预期输出示例
- **并且** 系统管理员必须审核后才能公开
- **并且** 贡献者必须获得署名

## 修改需求

无（这是新增功能）

## 移除需求

无
