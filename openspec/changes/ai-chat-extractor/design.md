# Design: AI Chat Extractor

## 上下文

### 当前状态
这是一个全新的项目，不存在现有系统需要迁移或兼容。项目目标是从零开始构建一个跨平台的 AI 对话管理和内容分发系统。

### 业务背景
AI 对话内容分散在不同平台（Gemini、豆包等），用户无法统一管理和二次利用。本项目通过浏览器插件采集对话、后端 AI 加工、自动渲染分享图、Web 平台展示，形成完整的"采集-加工-分发"闭环。

### 技术约束
- **浏览器环境限制**：Chrome Extension Manifest V3 对后台脚本、跨域请求、权限管理有严格限制
- **AI API 限制**：DeepSeek API 有调用频率限制、Token 配额限制、成本控制要求
- **渲染性能**：Puppeteer 启动 Chrome 实例资源消耗大，需要实例池和队列管理
- **部署环境**：需要具备海外访问能力的服务器（兼顾 Gemini 访问），可能需要代理或 CDN

### 利益相关者
- **终端用户**：使用浏览器插件采集对话，通过 Web 平台查看和分享内容
- **管理员**：通过密钥 URL 访问管理后台，管理内容、编辑总结、控制系统配置
- **开发者**：需要清晰的模块划分和 API 设计，便于后续维护和扩展

## 目标 / 非目标

### 目标

**第一优先级（MVP）**：
- 实现浏览器插件的基础采集功能（Gemini 和豆包平台）
- 完成后端 API 接收和存储对话数据
- 集成 DeepSeek API 生成详细汇总和社媒摘要
- 提供基础的 Web 展示页和管理后台

**第二优先级（Visual）**：
- 实现 Puppeteer 渲染引擎和至少 2 种模板（Bento UI、Newsletter）
- 提供模板选择和预览功能
- 优化渲染性能（实例池、队列管理）

**第三优先级（Archive）**：
- 完善 Web 平台的搜索、筛选、分页功能
- 实现内容编辑、批量操作功能
- 优化响应式设计和用户体验

**第四优先级（Integration）**：
- 预留 NotebookLM、Notion 等工具的导出接口
- 支持更多 AI 平台（Claude、ChatGPT 等）

### 非目标

**明确排除**：
- **用户账户体系**：不实现注册、登录、权限管理，使用固定密钥 URL 访问后台
- **实时通信**：不使用 WebSocket 或 Server-Sent Events，所有交互通过 HTTP 请求
- **内容审核**：不实现自动内容审核，依赖管理员手动管理
- **付费功能**：不实现订阅、支付、配额控制等功能
- **多租户**：不支持多用户隔离，所有数据共享（公开/隐藏控制即可）
- **移动端原生应用**：专注于 Web 平台，不开发 iOS/Android 应用

## 决策

### 1. 浏览器插件技术栈：Chrome Extension Manifest V3 + Vanilla JS

**决策**：使用 Chrome Extension Manifest V3 规范，插件核心逻辑使用 Vanilla JavaScript（不依赖框架）。

**理由**：
- **兼容性**：Manifest V3 是 Chrome 官方强制要求，V2 已被废弃
- **轻量级**：插件功能相对简单（DOM 操作、HTTP 请求），不需要 Vue/React 的复杂度
- **性能**：Vanilla JS 体积小、加载快，符合浏览器插件的最佳实践
- **维护成本**：避免框架版本升级、构建配置等额外负担

**考虑过的替代方案**：
- **Vue3 + Vite**：插件功能相对简单，引入框架增加复杂度和打包体积
- **React + CRXJS**：与 Vue 类似，过度设计

### 2. 后端框架：Node.js + Fastify

**决策**：使用 Fastify 作为后端 Web 框架。

**理由**：
- **性能优势**：Fastify 比 Express 快 2-3 倍，低开销适合高并发场景
- **Schema 验证**：内置 JSON Schema 验证，简化请求参数校验
- **TypeScript 支持**：原生支持 TypeScript，提升代码质量和开发体验
- **插件生态**：与 Puppeteer 生态兼容良好（都基于 Node.js）
- **异步优先**：基于 Promise 和 async/await，适合 AI API 调用等 I/O 密集型任务

**考虑过的替代方案**：
- **Express**：成熟稳定，但性能不如 Fastify，缺少内置验证
- **Koa**：轻量优雅，但需要额外配置中间件，生态不如 Fastify
- **NestJS**：功能强大但过于重量级，学习曲线陡峭

### 3. 数据库：SQLite（初期）→ MongoDB（后期）

**决策**：初期使用 SQLite，后期根据数据量和查询需求迁移到 MongoDB。

**理由**：
- **SQLite 优势**：
  - 零配置，无需独立数据库服务
  - 文件级存储，备份和迁移简单
  - 适合 MVP 阶段（数据量小、并发低）
  - 支持完整的 SQL 语法，查询灵活
- **MongoDB 优势**（后期迁移原因）：
  - 灵活的文档模型，适合存储变长的对话内容和 AI 生成结果
  - 原生支持 JSON 查询，与插件数据格式完美匹配
  - 水平扩展能力强，适合高并发场景
  - 云服务支持（如 MongoDB Atlas），便于部署

**迁移计划**：
- 使用 ORM 或数据访问层抽象数据库操作（如 Prisma、Mongoose）
- 设计统一的 Repository 接口，减少迁移成本
- 提供数据迁移脚本（SQLite → MongoDB）

**考虑过的替代方案**：
- **PostgreSQL**：功能强大但过于重量级，初期不需要
- **MySQL**：与 PostgreSQL 类似，文档存储不如 MongoDB 灵活

### 4. AI 模型选择：DeepSeek-V3（主要） + DeepSeek-R1（可选）

**决策**：使用 DeepSeek-V3 作为主要模型（性价比高），对复杂对话可选用 DeepSeek-R1（推理能力更强）。

**理由**：
- **成本优势**：DeepSeek 定价远低于 GPT-4、Claude API，适合高频调用
- **中文优化**：对中文对话的理解和生成能力优秀
- **API 兼容性**：API 设计与 OpenAI 兼容，集成成本低
- **V3 vs R1**：V3 适合大多数总结任务，R1 适合复杂推理（可选）
- **国产服务**：无需海外支付，访问稳定

**成本控制策略**：
- 详细汇总使用 V3（输入长、输出长，选择性价比高的模型）
- 社媒摘要使用 V3（字数限制 280，成本低）
- 设置单次调用 Token 上限（如 4000 tokens）
- 实现请求缓存（相同对话不重复生成）

**考虑过的替代方案**：
- **GPT-4**：能力强但成本高，不适合 MVP
- **Claude API**：性价比不如 DeepSeek
- **本地模型（Llama 等）**：部署复杂，需要 GPU 资源

### 5. 图片渲染：Puppeteer + 实例池 + 任务队列

**决策**：使用 Puppeteer 启动 Headless Chrome 渲染 HTML，实现实例池和任务队列管理。

**理由**：
- **渲染质量**：Chrome 渲染引擎最接近真实浏览器效果
- **模板灵活**：使用 HTML + CSS 开发模板，开发效率高
- **生态成熟**：Puppeteer 是业界标准，社区资源丰富
- **实例池必要性**：避免频繁启动/关闭 Chrome（每次 1-2 秒）
- **任务队列必要性**：防止并发请求过多导致资源耗尽

**实现细节**：
- **实例池配置**：
  - 预启动 3-5 个 Puppeteer 实例
  - 使用对象池模式管理实例获取和释放
  - 定期清理空闲实例（如超过 10 分钟未使用）
- **任务队列**：
  - 使用内存队列或 Redis 队列（如 Bull）
  - 限制并发渲染数量（如最多 3 个）
  - 实现 FIFO 排队，超时自动移除
- **性能优化**：
  - 缓存模板静态资源（CSS、字体）
  - 禁用不必要的 Chrome 功能（图片加载、GPU 加速）
  - 使用 `--no-sandbox` 标志（Docker 环境）

**考虑过的替代方案**：
- **Playwright**：功能类似但更重，Puppeteer 足够
- **Canvas + Node-canvas**：需要手动绘制，开发效率低
- **前端渲染 + html2canvas**：依赖用户浏览器，不一致性高

### 6. Web 前端框架：React + Next.js（可选）

**决策**：初期使用简单的 HTML + 模板引擎（如 EJS、Handlebars），后期复杂化后迁移到 Next.js。

**理由**：
- **初期简单方案**：
  - Web 平台功能相对简单（列表展示、详情页、表单）
  - 服务端渲染（SSR）更利于 SEO
  - 无需构建工具，开发速度快
- **后期 Next.js 迁移原因**：
  - 交互复杂化（实时编辑、拖拽、状态管理）
  - 需要 React 生态（UI 库、状态管理、路由）
  - SEO 优化（SSR、SSG、ISR）

**考虑过的替代方案**：
- **Vue + Nuxt**：与 React 类似，团队熟悉度可能影响选择
- **SvelteKit**：生态不如 Next.js 成熟

### 7. 部署架构：单服务器 + Docker（初期）→ 分布式（后期）

**决策**：初期使用单服务器部署（Docker 容器化），后期根据负载分布式部署。

**理由**：
- **初期架构**：
  - 所有服务（后端、数据库、Puppeteer）部署在同一服务器
  - 使用 Docker Compose 编排服务
  - 适合 MVP 阶段（用户量小、请求量低）
- **后期扩展**：
  - 分离 Puppeteer 服务到独立容器（资源隔离）
  - 使用 Nginx 反向代理和负载均衡
  - 数据库迁移到云服务（如 MongoDB Atlas）

**服务器配置建议**：
- **最低配置**：2 核 CPU、4GB 内存、40GB 存储（适合 MVP）
- **推荐配置**：4 核 CPU、8GB 内存、100GB 存储（支持 Puppeteer 实例池）
- **海外服务器**：如 AWS、Vultr、DigitalOcean（兼顾 Gemini 访问）

**考虑过的替代方案**：
- **Serverless（如 AWS Lambda）**：不适合 Puppeteer（需要长时间运行）
- **Kubernetes**：初期过于复杂，运维成本高

### 8. 安全性设计

**决策**：实现多层安全防护，重点保护 API、管理后台和用户数据。

**措施**：
- **API 安全**：
  - CORS 白名单（仅允许插件域名访问）
  - 请求频率限制（Rate Limiting，如每分钟 10 次）
  - 输入验证和清理（防止 SQL 注入、XSS）
- **管理后台安全**：
  - 固定密钥 URL（至少 16 个随机字符）
  - 会话 Cookie（HttpOnly、Secure、SameSite）
  - 会话过期机制（默认 7 天）
- **数据隐私**：
  - 不记录用户的敏感信息（插件仅发送对话内容）
  - 提供数据删除功能（物理删除）
  - API 调用日志脱敏（不记录完整对话内容）

## 风险 / 权衡

### 1. Puppeteer 性能风险

**风险**：Puppeteer 启动 Chrome 实例消耗大量内存和 CPU，高并发时可能导致服务器资源耗尽。

**缓解措施**：
- 实现实例池和任务队列，限制并发数量
- 设置请求超时（30 秒）和自动重试机制
- 监控资源使用，超过阈值时拒绝新请求
- 考虑使用 Puppeteer 的_cluster 模式（多进程）

### 2. AI API 成本风险

**风险**：用户频繁采集对话可能导致 API 调用成本超预期。

**缓解措施**：
- 设置每日调用上限（如插件端限制每天最多 10 次）
- 实现请求缓存（相同对话不重复生成）
- 监控成本消耗，超过阈值时发送告警
- 提示词优化（减少不必要的 Token 消耗）

### 3. 浏览器插件兼容性风险

**风险**：Gemini 和豆包的页面 DOM 结构可能频繁变化，导致采集功能失效。

**缓解措施**：
- 设计灵活的 DOM 选择器（使用多种备选方案）
- 实现插件自动更新机制（通过 Chrome Web Store）
- 提供"手动报告问题"功能，快速收集用户反馈
- 定期测试和更新插件适配逻辑

### 4. 部署环境限制

**风险**：需要海外服务器访问 Gemini，但国内用户访问海外服务器可能速度慢。

**缓解措施**：
- 使用 CDN 加速静态资源（如 Cloudflare）
- 部署多地域服务器（如香港、新加坡）
- 插件端支持代理配置（允许用户自定义 API 地址）

### 5. 数据库迁移风险

**风险**：从 SQLite 迁移到 MongoDB 可能导致数据丢失或服务中断。

**缓解措施**：
- 使用 ORM 抽象层，减少数据库依赖
- 实现零停机迁移（先同步后切换）
- 提供详细的迁移脚本和回滚方案
- 在测试环境充分验证后再执行生产迁移

## 部署计划

### 第一阶段：本地开发（Week 1-2）

**目标**：完成 MVP 的核心功能开发和本地测试。

**步骤**：
1. 搭建开发环境（Node.js、SQLite、Puppeteer）
2. 实现后端 API 接收和存储逻辑
3. 开发浏览器插件基础采集功能
4. 集成 DeepSeek API 生成总结
5. 本地测试端到端流程

**验收标准**：
- 插件能够成功采集 Gemini 对话并发送到本地后端
- 后端能够调用 DeepSeek API 生成总结
- 数据能够正确存储到 SQLite

### 第二阶段：部署测试环境（Week 3）

**目标**：部署到测试服务器，验证真实环境运行。

**步骤**：
1. 准备云服务器（推荐 Vultr 或 DigitalOcean）
2. 使用 Docker Compose 部署所有服务
3. 配置域名和 SSL 证书（Let's Encrypt）
4. 更新插件配置（指向测试服务器）
5. 邀请小范围用户测试

**验收标准**：
- 插件能够正常采集和上传对话
- Web 平台能够展示公开内容
- 管理后台能够管理内容和配置

### 第三阶段：生产环境部署（Week 4）

**目标**：正式上线，准备迎接真实用户。

**步骤**：
1. 准备生产服务器（更高配置）
2. 配置监控和日志（如 Sentry、Grafana）
3. 设置备份策略（数据库、渲染图片）
4. 更新插件到 Chrome Web Store
5. 发布公告，开放使用

**验收标准**：
- 服务稳定性达到 99.5% 以上
- API 响应时间 < 2 秒（P95）
- 渲染成功率 > 95%

### 回滚策略

- **数据库回滚**：保留迁移前的 SQLite 备份，支持快速回退
- **代码回滚**：使用 Git 标签管理版本，支持一键回退到上一版本
- **配置回滚**：使用配置管理工具（如 Consul、etcd）保存历史配置

## 待决问题

### 1. 是否需要支持更多 AI 平台？

**背景**：当前设计仅支持 Gemini 和豆包，但用户可能需要采集 Claude、ChatGPT 等平台的对话。

**待决策**：
- 是否在 MVP 中支持其他平台？
- 优先级排序（用户量、技术难度）

**建议**：先完成 Gemini 和豆包的稳定版本，收集用户反馈后再决定。

### 2. 是否实现用户账户体系？

**背景**：当前设计使用固定密钥 URL 访问后台，不支持多用户隔离。

**待决策**：
- 是否需要支持多个管理员？
- 是否需要用户级别的数据隔离？

**建议**：MVP 阶段使用固定密钥，后期根据需求决定是否引入账户体系。

### 3. Puppeteer 服务是否独立部署？

**背景**：Puppeteer 资源消耗大，可能影响其他服务的稳定性。

**待决策**：
- 是否在初期就分离 Puppeteer 服务？
- 如何实现服务间通信（HTTP、消息队列）？

**建议**：初期部署在同一服务器，使用 Docker 容器隔离，后期资源紧张时再分离。

### 4. 是否实现实时通知？

**背景**：用户可能希望在插件中收到"总结已生成"的通知。

**待决策**：
- 是否需要 WebSocket 或轮询机制？
- 通知的触发条件（成功、失败、超时）

**建议**：MVP 不实现实时通知，用户手动刷新查看状态。

### 5. AI 模型选择策略

**背景**：DeepSeek-V3 和 R1 成本和能力差异，如何选择最合适的模型？

**待决策**：
- 是否根据对话长度自动选择模型？
- 是否允许用户手动选择模型？

**建议**：初期默认使用 V3，后期根据成本和质量数据优化选择策略。
